# UI/UX 設計指引與協作原則

> 狀態：現行規範（Living Document）  
> 最後更新：2026-08-27  
> 適用範圍：Jwander Temp Storage 的公開頁面、檔案瀏覽、邀請流程與管理介面

## 1. 文件目的

這份文件是 UI/UX 決策的共同基準，目的是讓不同地點、不同時間進行開發時，仍能維持相同的產品語言與設計方向。

新增頁面、調整元件或修改互動時，應同時檢查：

1. 是否符合本文件的產品原則與使用者心智模型。
2. 是否沿用既有的語意色彩、版型與元件行為。
3. 是否同時支援亮色、暗色、鍵盤操作與手機尺寸。
4. 若刻意偏離本文件，是否在同一個變更中補充原因並更新文件。

即使本儲存庫不公開，文件與畫面範例仍不得包含正式環境的管理 token、邀請存取碼、私密網址、Cookie、Cloudflare 機密或可識別個人的檔名。

## 2. 規範優先順序

遇到規格衝突時，依下列順序判斷：

1. 產品安全與權限邏輯。
2. 本文件描述的產品原則與使用者體驗。
3. `public/cloud-drive.css` 內的現行設計 token 與元件實作。
4. `public/index.html` 與 `public/app.ts` 的現行頁面結構和互動。

長期設計原則只維護在本文件；實際 token 與元件樣式只維護在 `public/cloud-drive.css`。不要另外建立平行的設計系統文件，避免同一規則出現多個版本。

## 3. 產品定位

這是一個私有、暫時性的檔案中繼與瀏覽工具，使用體驗接近熟悉的雲端硬碟，但不追求企業檔案管理系統的複雜度。

核心印象應是：

- 安靜、可靠、直接。
- 像私人雲端硬碟，而不是科技產品展示頁。
- 清楚知道自己目前能做什麼，以及檔案會保留多久。
- 管理能力完整，但不讓一般使用者看到不必要的管理複雜度。

風格名稱為 **Quiet Utility Minimalism（安靜的實用極簡）**。

### 要保留的特質

- 暖中性色背景，低彩度、低干擾。
- 清楚的資訊層級與適量留白。
- 熟悉的檔案卡片、篩選器、容量與狀態表達。
- 單一、克制的紫棕色作為重點色。
- 細邊框、柔和陰影與適度圓角。
- 亮暗模式具備相同的資訊辨識力。

### 不採用的方向

- 藍紫漸層、霓虹、發光邊框或明顯「科技感」。
- 裝飾性的 3D、玻璃擬態堆疊或複雜背景動畫。
- 為了視覺效果犧牲可讀性、操作速度或檔案資訊密度。
- 使用 Emoji 當作結構性圖示。
- 不同頁面各自發展一套色彩、陰影或按鈕樣式。

## 4. 核心 UX 原則

### 4.1 任務優先

每個頁面只突出當下最重要的工作：驗證邀請、上傳檔案、瀏覽檔案或管理邀請。主要動作應靠近相關欄位，不把關鍵 CTA 放在遠離操作內容的位置。

### 4.2 使用熟悉的雲端硬碟心智模型

檔案使用卡片、縮圖、類型、大小與時間等熟悉資訊呈現。篩選與下載應可直接理解，不創造需要學習的新手勢或自訂術語。

### 4.3 權限必須可預期

邀請分為兩種明確模式：

- **上傳與瀏覽**：可在額度內上傳，也可瀏覽與下載。
- **僅瀏覽與下載**：對外顯示上傳檔案數 `0`、總容量 `0 B`，且後端拒絕所有上傳請求。

一般邀請的上傳額度用完後，只停止新的上傳；只要邀請與登入工作階段仍有效，瀏覽與下載不受影響。不能只在 UI 隱藏按鈕，權限必須由後端實際執行。

### 4.4 狀態永遠說清楚

驗證、載入、上傳、成功、失敗、額度用完、權限不足與空資料都要有文字回饋。顏色只能輔助，不能成為唯一訊號。

### 4.5 行動裝置不是縮小版桌面

在窄螢幕上優先保留核心工作，導覽改到底部、網格改為單欄、水平排列改為垂直堆疊，並保留安全區與觸控空間。

### 4.6 無障礙是基礎規格

鍵盤、焦點、語意標籤、對比與減少動態效果，皆屬交付條件，不是後續加分項目。

## 5. 資訊架構與頁面責任

| 路徑        | 頁面名稱   | 主要責任                                                              |
| ----------- | ---------- | --------------------------------------------------------------------- |
| `/`         | 檔案暫存區 | 驗證邀請、顯示邀請與容量狀態、選擇或拖放檔案、呈現上傳佇列            |
| `/files`    | 所有檔案   | 驗證存取、瀏覽與篩選共享檔案、下載檔案；管理員可看到管理操作          |
| `/file/:id` | 檔案詳情   | 預覽支援的檔案、顯示中繼資料與下載操作                                |
| `/admin`    | 管理控制台 | 管理員驗證、建立／命名／重新簽發／撤銷邀請；檔案瀏覽仍集中於 `/files` |

頂層導覽維持兩個主要目的地，避免增加重複入口。管理員登入後可以調整第一個入口的語意，但不能破壞使用者對「上傳／管理」與「所有檔案」兩個區域的理解。

## 6. 命名與文案

### 固定產品用語

| 概念       | 使用文字     |
| ---------- | ------------ |
| 首頁標題   | 檔案暫存區   |
| 瀏覽頁標題 | 所有檔案     |
| 管理頁標題 | 管理控制台   |
| 授權物件   | 邀請         |
| 使用者輸入 | 存取碼       |
| 完整權限   | 上傳與瀏覽   |
| 唯讀權限   | 僅瀏覽與下載 |

### 文案語氣

- 使用繁體中文，簡短、具體、以動作為中心。
- 優先說明「發生什麼事」與「下一步怎麼做」。
- 一般使用者文案避免 API、節點、物件儲存等實作術語。
- 危險操作明確指出影響範圍，不用模糊的「確定嗎？」。
- 按鈕使用動詞，例如「驗證並進入暫存區」、「建立並複製邀請」、「下載檔案」。
- 不在主標題上方加入重複的小標；頁面名稱本身應足以建立層級。

### 7.1 色彩

所有元件必須使用語意變數，不在元件內新增無意義的零散色碼。

| `--focus`          | `#684B8D` | `#C8B3E2` | 鍵盤焦點環                     |

新顏色必須先回答它代表的語意；若只是為單一元件「看起來更漂亮」，原則上不新增。

### 7.2 亮暗模式

- 預設為亮色，使用者可手動切換，偏好儲存在 `localStorage`。
- 兩個模式必須使用相同資訊層級，而不是把亮色直接反相。
- 正文對背景至少達 WCAG AA 4.5:1；大型文字與非文字 UI 至少 3:1。
- 邊框、停用、Hover、Focus、成功、警告與錯誤狀態都要分別檢查。
- 調整主題色時，同步更新瀏覽器 `theme-color`。

### 7.3 字體與層級

- 內文字體：`Segoe UI Variable`、`Noto Sans TC`、`PingFang TC`、`Microsoft JhengHei`、`system-ui`。
- 標題字體：`Segoe UI Variable Display`、`Noto Sans TC`、`sans-serif`。
- 正文基準：`16px / 1.5`；說明文字通常使用 `1.6–1.8` 行高。
- 頂層 H1：桌面 `clamp(3rem, 5vw, 4.8rem)`；手機 `clamp(2.75rem, 12vw, 3.25rem)`。
- H1 使用約 `660` 字重、緊縮字距，三個頂層頁面必須保持相同尺寸與起始位置。
- 標題與標籤不使用全粗體堆疊；資訊層級同時依靠尺寸、間距與色彩建立。
- 檔案類型等短代碼可使用 `Cascadia Mono`／`Consolas`，正文不可改用等寬字體。

### 7.4 間距、寬度與圓角

- 基礎間距採 4px／8px 節奏，常用值為 `4, 8, 12, 16, 20, 24, 32, 40, 48, 64px`。
- 內容最大寬度為 `1240px`；桌面左右 gutter 為 `20px`，手機為 `12px`。
- 元件小圓角約 `9–12px`，卡片約 `15–20px`，主要面板約 `20–26px`，膠囊狀態使用 `999px`。
- 圓角大小反映層級，不應隨意為每個元件指定新值。
- 陰影維持三層：微幅分離、一般面板、浮層／Toast；不使用厚重或彩色光暈。

### 7.5 圖示與影像

- 使用同一套線性 SVG 視覺語言，線寬約 `1.7`、圓角端點與接點。
- 品牌標誌固定使用雲朵與字母 J 組成的輪廓。標準彩色 icon 統一使用 `public/favicon.svg` 的品牌主色圓角矩形搭配白色標誌版本，適用於 masthead、瀏覽器 favicon 與 README 主視覺，確保亮暗背景皆有清楚對比。
- `public/brand-mark.svg` 只保留給 Safari pinned tab 等必須使用單色遮罩的情境；原始 SVG、點陣輸出與概念展示稿保存在 [`assets/brand/`](./assets/brand/) 中，不直接作為頁面內容載入。
- 圖示不能取代必要的文字；純圖示按鈕必須有 `aria-label`。
- 不使用 Emoji 作為導覽、狀態或操作圖示。
- 圖片縮圖使用 `object-fit: cover`，並預留尺寸避免載入造成版面跳動。
- 無縮圖時，以檔案類型卡面取代，不顯示破圖圖示。

## 8. 版型與響應式

### 桌面

- Masthead 為置中的三欄結構：品牌、主要導覽、操作區；保持黏附但不遮住內容。
- 頂層內容在 Masthead 下使用一致的 H1 起點與留白。
- 檔案網格預設三欄；管理區可使用多欄表單，但同一列欄位要有明確關聯。

### Breakpoints

| 寬度      | 行為                                                             |
| --------- | ---------------------------------------------------------------- |
| `> 980px` | 檔案三欄、完整桌面配置                                           |
| `≤ 980px` | 檔案兩欄、管理工作區收為單欄、隱藏次要保留期限標籤               |
| `≤ 760px` | 底部雙項導覽、檔案單欄、表單單欄、權限選擇單欄、主要內容垂直排列 |
| `≤ 500px` | 進一步縮減面板 padding，動作按鈕可換行並平分寬度                 |

### 手機要求

- 最小支援寬度 `320px`，主要驗收尺寸為 `375px`。
- 不得出現整頁水平捲動。
- 底部導覽需加入 `env(safe-area-inset-bottom)`，內容也要預留對應底部空間。
- 主要觸控目標至少 `44×44px`；底部導覽至少 `48px` 高。
- 不依賴 Hover 顯示必要功能。
- 文字放大或名稱較長時優先換行，不讓內容被截斷到失去意義。

## 9. 元件與互動規範

### 9.1 Masthead 與導覽

- Masthead 桌面為 sticky，手機導覽移至固定底部。
- 當前頁使用實色表面、文字加深與輕陰影表示，不只依靠顏色。
- 導覽項目同時包含圖示與文字。
- 頂層導覽已有相同目的地時，不在頁面 Header 或空狀態重複放置「前往上傳／返回管理」連結。
- 管理工作階段依既有到期機制結束，不另外占用頁面空間提供結束 Session 按鈕。
- 主題切換按鈕為 `44×44px`，並同步更新 `aria-pressed` 與可理解的 `aria-label`。

### 9.2 按鈕

- Primary：每個工作區最多一個主要 CTA，使用 `--primary`。
- Secondary：白／浮起表面加邊框，用於返回、取消、重新整理等次要動作。
- Text button：用於低優先、局部操作，不與 Primary 爭奪視覺重量。
- Danger：只用於刪除、撤銷等破壞性操作，並與一般動作保持距離。
- 高度至少 `44px`，主要按鈕目前為 `46px`。
- Hover／Focus／Active 使用 `180–240ms` 的色彩、陰影或 1px 位移回饋，不做造成版面抖動的縮放。
- 非同步送出期間必須停用觸發按鈕；完成後顯示成功或錯誤訊息。

### 9.3 表單

- 每個欄位都有可見 Label，不以 Placeholder 代替名稱。
- 一般輸入框高度至少 `48px`，圓角約 `11px`。
- Focus 使用 `3px` 半透明焦點環，不能移除而不替代。
- 錯誤訊息應靠近相關欄位，並說明修正方式。
- 數量與容量欄位使用合適的 `type`／`inputmode`。
- 不適用的欄位使用真正的 `disabled` 屬性與降階視覺。
- 權限選擇使用 `fieldset + legend + radio`；選擇「僅瀏覽與下載」時，額度欄位必須停用並對外呈現 `0 / 0 B`。
- 邀請標籤預設使用管理者瀏覽器的本地時間產生：上傳邀請為 `upload-YYYYMMDD-HHmmss`，僅瀏覽邀請為 `browse-YYYYMMDD-HHmmss`；使用者手動改名後不得自動覆寫。

### 9.4 驗證 Gate 與面板

- 驗證區最大寬度 `720px`，維持單一明確任務。
- 面板以邊框、背景與適度陰影區隔，不加入裝飾性圖片。
- 驗證失敗時保留輸入與重試路徑，不讓使用者面對空白畫面。

### 9.5 檔案卡片與檔案列表

- 卡片優先呈現：縮圖／類型、檔名、檔案類型、大小與時間。
- 檔名允許換行並使用 `overflow-wrap: anywhere`，不可因長檔名破壞網格。
- 圖片、影片、音訊與其他檔案可使用不同的低彩度背景，但資訊不能只靠顏色辨識。
- 卡片 Hover 僅輕微上浮；縮圖最多小幅放大，不加入循環動畫。
- 載入中、空資料與載入失敗都要有獨立狀態；失敗狀態提供重試。

### 9.6 上傳區與容量

- 拖放區同時提供可見的「選擇檔案」按鈕，不能只支援拖曳。
- 拖曳、Focus 與 Hover 共用一致的高亮邏輯。
- 佇列逐檔顯示等待、保留額度、上傳中、完成、失敗或取消狀態。
- 容量進度條搭配數字說明；不能只靠長條顏色傳達剩餘容量。
- 無上傳權限或額度不可用時，停用整個上傳入口並說明原因。

### 9.7 Toast、狀態與對話框

- Toast 位於桌面右下、手機底部導覽上方，使用 `aria-live="polite"`。
- 一般 Toast 約 3–5 秒自動消失；目前實作為 3.6 秒。
- 錯誤 Toast 使用 danger 語意色，但仍需有可理解文字。
- 刪除、撤銷等不可逆操作使用確認對話框，預設焦點與按鈕順序應降低誤觸。
- 對話框需可由鍵盤關閉，並在關閉後將焦點還給觸發元件。

## 10. 動態效果

- 動態效果只用於說明狀態變化與操作因果，不做純裝飾表演。
- 一般微互動使用 `150–300ms`；目前多數元件採 `180ms`，主題切換與進度約 `220–240ms`。
- 優先動畫 `opacity` 與 `transform`，避免頻繁動畫寬高或位置造成 reflow；容量進度條是有明確語意的例外。
- 不引入 GSAP 或大型動畫套件，除非有無法用 CSS 完成的明確產品需求。
- `prefers-reduced-motion: reduce` 時，移除平滑捲動並將動畫／轉場縮至接近零。
- 不使用無限循環裝飾動畫；載入指示器例外，但仍須具備可讀文字。

## 11. 無障礙基準

每次 UI 變更至少確認：

- 頁面有一個可見且語意正確的 H1；三個頂層頁面層級一致。
- 提供「跳到主要內容」連結。
- 所有功能可使用鍵盤完成，Tab 順序符合畫面順序，沒有鍵盤陷阱。
- `:focus-visible` 清楚可見，不能只靠 Hover。
- 表單使用 `label`／`for`，群組選項使用 `fieldset`／`legend`。
- 純圖示按鈕有可描述行為的 `aria-label`。
- 動態結果、上傳狀態與 Toast 使用適當的 `aria-live`，但避免重複播報。
- 顏色不是唯一狀態指標；同時使用文字、圖示、邊框或形狀。
- 正文對比至少 4.5:1，UI 邊界與大型文字至少 3:1。
- 支援 `prefers-reduced-motion`，且瀏覽器縮放至 200% 仍可操作。
- 圖片有正確替代文字；純裝飾 SVG 使用 `aria-hidden="true"`。

## 12. 效能與穩定性

- 非首屏縮圖使用 Lazy Loading，並固定預覽尺寸以避免 CLS。
- 不為單一效果加入大型第三方前端依賴。
- DOM 更新盡量批次進行，避免在大型檔案列表中交錯讀寫 Layout。
- 檔案持續增加時，優先使用分頁／載入更多；超過約 50 個同時可見項目時評估虛擬化。
- 按鈕送出後立即提供 Busy／Disabled 狀態，長操作提供進度或可理解的載入文字。
- 路由可直接透過 URL 開啟，重新整理後不應失去所在頁面的基本語意。

## 13. 跨地開發流程

### 開始修改前

1. 先讀本文件與相關功能規格。
2. 檢查 `public/cloud-drive.css` 是否已有可重用 token 或元件。
3. 確認變更影響的權限、亮暗模式、桌面與手機狀態。
4. 若要新增新的視覺模式，先寫清楚它解決的使用者問題。

### 實作時

- 優先擴充既有元件，不建立名稱不同但視覺相同的副本。
- 顏色使用語意 token，間距遵循 4px／8px 節奏。
- UI 權限控制必須與後端驗證同步修改。
- 文案沿用第 6 節的固定用語。
- 同一個變更中補齊測試、文件與必要的資料庫 migration。

### 完成前驗收

- [ ] `375px`、`760px` 附近、`980px` 附近與 `1440px` 皆無水平溢位。
- [ ] 亮色與暗色都檢查過正文、邊框、Focus、Disabled 與狀態色。
- [ ] 鍵盤可完成主要流程，Focus 順序合理。
- [ ] 所有觸控目標至少 `44×44px`，相鄰目標不容易誤觸。
- [ ] Loading、Empty、Error、Success、Disabled 狀態皆有處理。
- [ ] `prefers-reduced-motion` 下沒有必要資訊依賴動畫出現。
- [ ] 長檔名、長邀請名稱、零額度與額度用完不會破版。
- [ ] 僅瀏覽邀請可瀏覽／下載，且前後端都無法上傳。
- [ ] Lint、TypeScript、測試與 Production Build 通過。

建議使用以下指令：

```powershell
pnpm lint
pnpm typecheck
pnpm test
pnpm build:client
```

## 14. 變更設計規範的方式

設計規範可以演進，但不應在沒有記錄的情況下漂移。若要改變色票、字級、導覽、權限呈現或核心元件，請在變更說明中記錄：

```md
### UI/UX 決策

- 問題：目前哪個使用情境有困難？
- 決定：要改成什麼？
- 理由：為什麼比現況更好？
- 影響：哪些頁面、權限、裝置與狀態會受到影響？
- 驗證：使用哪些尺寸、主題、鍵盤流程與測試確認？
```

若決策成為長期規則，必須同步更新本文件；若只是單一頁面的合理例外，應在對應規格文件中說明，不要默默偏離。
